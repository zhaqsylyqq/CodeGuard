# CodeGuard: руководство по проекту (для команды)

Этот файл объясняет, что мы сделали, что где лежит и как это работает. После него вы сможете запустить проект
и объяснить каждый шаг на защите.

## 1. О чём проект

**Задача:** по куску Python-кода определить, **есть ли в нём баг** (buggy) или это **исправленная** версия (fixed).

**Данные:** CTSSB-1M, около миллиона реальных исправлений багов из GitHub. Каждое исправление хранится как *diff*
(git-разница: что убрали, что добавили).

**Что сделано на текущий момент:**
1. `01_data.ipynb`: из сырых данных получили чистые, без утечки, пары «код с багом / исправленный код».
2. `02_baseline.ipynb`: простая модель (TF-IDF + логистическая регрессия). Она угадывает на уровне случайного
   (accuracy 0,503), и мы объяснили почему. Это точка отсчёта для следующих моделей.
3. Добавлена реализация этапов 3–5: BiLSTM, DeepSeek baseline, LoRA/QLoRA. Полные эксперименты
   на CTSSB ещё предстоят; подробности и команды — в разделах 13–18.

## 3. Что такое parquet

**Parquet** (`.parquet`) это формат файла для таблиц, как CSV, но лучше для больших данных:

- **компактнее.** Данные сжаты, поэтому файлы меньше. Наш `pool.parquet` занимает 140 МБ, а в CSV был бы в несколько раз больше;
- **быстрее читается.** Читается напрямую в таблицу pandas, без разбора текста;
- **хранит типы колонок** (число, текст, True/False), в CSV всё приходится угадывать заново;
- **безопасен для кода.** В CSV сложные тексты с переводами строк и запятыми легко ломаются, а в parquet нет.

Читать и писать просто:
```python
import pandas as pd
df = pd.read_parquet("data/processed/train.parquet")   # прочитать
df.to_parquet("data/processed/train.parquet", index=False)  # записать
```
Открыть parquet в блокноте нельзя (это бинарный формат), его читают через pandas.

## 5. Что такое `src` (source)

`src` означает **source**, то есть «исходный код». Здесь лежит **код, который можно использовать повторно**.

Зачем нужна отдельная папка, а не код прямо в ноутбуке:
- функции используют оба ноутбука (`01` и `02`), а потом будут использовать и следующие;
- функции можно **тестировать** (см. ниже), а код внутри ноутбука нельзя;
- ноутбук читается как рассказ, потому что в нём вызовы функций, а не сотни строк реализации.

В ноутбуке это подключается двумя строками:
```python
sys.path.append("../src")      # говорим Python, где искать наши функции
import data_utils as du         # дальше вызываем du.rebuild_snippets(...)
```

## 6. Что такое `tests`

**Тест** это маленькая программа, которая автоматически проверяет, что функция работает правильно.
Мы даём функции известный вход и сравниваем результат с тем, что ожидаем.

Пример: `rebuild_snippets` получает diff, и мы проверяем, что `buggy` и `fixed` получились именно такими, как нужно.

Запуск (из корня проекта):
```powershell
python -m pytest tests -q
```
В исходной версии было 9 тестов подготовки данных. С нейросетевыми зависимостями выполняются ещё 7 проверок.
Если какой-то тест падает, нужно выяснить причину перед экспериментами.

**Зачем это нам:**
- защита от повторения старого бага (тест про отступы);
- уверенность, что изменив код, ничего не сломали;
- на защите можно показать, что проект проверяется автоматически.

## 7. Ключевые функции (`src/data_utils.py`)

| Функция | Что делает | Зачем |
|---|---|---|
| `load_pool` | читает 10 архивов, оставляет нужные колонки и только `in_function`, сохраняет `pool.parquet` | сырые данные огромные, читаем один раз |
| `rebuild_snippets` | превращает diff в два текста (`buggy` и `fixed`) | в датасете нет готовых пар, только diff |
| `add_snippets` | применяет `rebuild_snippets` ко всей таблице | то же, для всех строк |
| `normalize_code` | убирает пробелы в конце строк и пустые строки, **оставляет отступы** | чтобы форматирование не мешало искать дубли |
| `code_hash` | считает короткий отпечаток (md5) нормализованного кода | быстро сравнивать тексты |
| `add_hashes` | добавляет колонки `buggy_hash`, `fixed_hash` | то же, для всех строк |
| `is_python2` / `add_python2_flag` | помечают код в стиле Python 2 (`print "x"`, `10L`...) | не удаляем, но хотим знать долю |
| `split_by_project` | делит на train/val/test 80/10/10 так, чтобы проект был только в одном сплите | иначе утечка: модель узнаёт проект, а не баг |
| `remove_cross_split_duplicates` | убирает из val/test код, который уже есть в train | один и тот же код бывает в разных проектах |
| `check_leakage` | проверяет, что нет общих проектов и сниппетов между сплитами | защита от утечки |
| `sample_pairs` | берёт случайные 4000 / 500 / 500 пар | для экспериментов нужен небольшой набор |
| `pairs_to_examples` | из пары делает два примера: buggy=1, fixed=0 | подготовка для классификатора |

### Как работает `rebuild_snippets` (самое важное)

Diff выглядит так:
```
@@ -45,7 +45,7 @@
 def test(self):                  <- пробел в начале: строка есть в ОБЕИХ версиях
-    x = datetime(1970, ...)      <- минус: только в версии с багом
+    x = datetime.fromtimestamp() <- плюс: только в исправленной
```
- строка с ` ` (пробел) попадает и в `buggy`, и в `fixed`;
- строка с `-` только в `buggy`;
- строка с `+` только в `fixed`;
- первый символ (` `, `-` или `+`) отбрасывается;
- строки `@@` и `\ No newline` пропускаются.

### Почему отступы сохраняются (исправленный баг)

В Python отступ меняет смысл программы. Старая версия кода схлопывала все пробелы, поэтому исправление, меняющее
только отступ, выглядело как «ничего не изменилось» и выбрасывалось. Теперь отступы остаются, и такие настоящие
исправления сохраняются. Это покрыто тестом `test_indentation_only_fix_is_not_a_duplicate`.

## 9. Как работает `02_baseline.ipynb`

1. Каждая пара превращается в два примера: buggy (метка 1) и fixed (метка 0).
2. **TF-IDF** превращает код в числа: для каждого токена считается, как часто он встречается в этом коде и как редко в остальных.
3. **Логистическая регрессия** учится по этим числам предсказывать метку.
4. Считаем метрики на val.

**Результат:** accuracy 0,503. То есть на уровне случайного. Причина: buggy и fixed версии одной пары почти полностью
совпадают по токенам, различие в одном операторе, а «мешок токенов» его не замечает.
Следующие модели должны читать код последовательно или уже знать много кода.

### Что значат метрики

- **Accuracy:** доля верных ответов.
- **Precision:** из того, что мы назвали багом, сколько действительно баг.
- **Recall:** из всех настоящих багов, сколько мы нашли.
- **F1:** среднее между precision и recall.

## 12. Известные ограничения (честно)

1. Ищутся только **точные** дубли; почти одинаковый код с другим именем переменной не находится.
2. Один и тот же текст может быть `buggy` в одной паре и `fixed` в другой (например, откат коммита), такие конфликты не считаются.
3. Датасет содержит только **однострочные** исправления, выводы нельзя переносить на любые баги.
4. Python 2 определяется регулярками, это эвристика с ложными срабатываниями.
5. Большинство сниппетов это фрагменты, а не полные программы, поэтому разбор через `ast` почти не работает.
6. Baseline на уровне случайного, это ожидаемо для мешка токенов.

## 15. Как устроена BiLSTM

Код превращается в последовательность Python-токенов. Сохраняются идентификаторы, литералы,
операторы, переводы строк и маркеры INDENT/DEDENT. На неполных или некорректно отступленных
фрагментах используется запасная регулярная токенизация: такие фрагменты не выбрасываются.
Это полезно, потому что CTSSB содержит куски функций, а не обязательно целые программы.

Словарь (до 20 000 токенов) строится **только по train**. Неизвестный токен получает UNK,
пустой фрагмент — один UNK, PAD нужен для дополнения последовательностей в batch.
По умолчанию берём первые 512 токенов. Всё после этого модель не видит: если исправление
оказалось дальше, задача становится неразличимой. Это ограничение нужно учитывать в отчёте.

Далее: Embedding(128) → двунаправленная LSTM(128) → Dropout → Linear → sigmoid.
Длины передаются в packed sequence: PAD не меняет итоговое представление.
Обучение — AdamW и binary cross entropy, ограничение нормы градиента до 1.
Из 10 эпох сохраняется лучшая по val loss, а метрики считаются уже на ней.
Поэтому это результат подбора на validation, а не независимая итоговая оценка.

В `runs/bilstm/best.pt` сохраняются веса, словарь, размеры модели, max_length и номер эпохи.
Для восстановления:

```python
import sys
import torch
sys.path.insert(0, "src")
from bilstm import BiLSTM, CodeDataset, collate_batch, predict
from torch.utils.data import DataLoader

checkpoint = torch.load("runs/bilstm/best.pt", map_location="cpu", weights_only=True)
model = BiLSTM(**checkpoint["config"])
model.load_state_dict(checkpoint["state_dict"])
# examples — таблица с колонками text, label (можно получить через load_examples).
loader = DataLoader(CodeDataset(examples, checkpoint["vocab"], checkpoint["max_length"]),
                    batch_size=32, collate_fn=collate_batch)
probabilities = predict(model, loader, torch.device("cpu"))
```

## 16. Как измеряем DeepSeek без обучения

Для каждого сниппета строится текстовое задание с просьбой ответить buggy или fixed.
Модель не генерирует свободный ответ: считаем log probability всех токенов продолжений
` fixed` и ` buggy`, складываем внутри каждого ответа и применяем softmax к двум суммам.
Нельзя сравнивать только первый токен: слово может разбиваться на несколько частей.
Начальный пробел перед ответом одинаков при оценке и обучении.

Если prompt не помещается в 512 токенов, сохраняем его начало с инструкцией и конец с кодом
и `Answer:`. Середина теряется. Резерв под ответ общий для обоих кандидатов, поэтому они
оцениваются на одинаковом контексте. Число усечённых примеров записывается в отчёт.

Полученное `p_buggy` — относительная вероятность **между двумя ответами**. Это не доказательство
наличия бага и не калиброванная уверенность. Короткий ответ может иметь преимущество из-за длины;
мы используем сумму log probability без нормировки по длине и явно фиксируем это правило.

По умолчанию скрипт оценивает только val. Test доступен явно через `--split test` после выбора
всех настроек. Для QLoRA baseline тоже лучше запускать с `--quantized`, чтобы изменение качества
не смешивалось с изменением точности весов.

## 17. LoRA и QLoRA: что обучается

Обычная LoRA оставляет базовые веса замороженными и обучает добавленные матрицы в q/k/v/o
проекциях attention. QLoRA дополнительно хранит базовые веса в NF4, с double quantization,
а вычисления выполняет в float16. Перед добавлением адаптера модель подготавливается
через `prepare_model_for_kbit_training`.

В коде включены gradient checkpointing и accumulation: маленький batch=2 накапливается
8 шагов, то есть эффективный batch=16 при одной GPU. Это экономит память, но не гарантирует,
что любая длина или большая модель поместится. При нехватке памяти сначала уменьшайте batch,
затем max_length, одинаково для сравниваемых запусков.

В обучающем примере метки prompt равны -100: loss считается только по правильному ответу.
PAD также замаскирован. Так модель учится классификации, а не воспроизведению кода из задания.
Лучший checkpoint выбирается по val loss, затем считаем те же accuracy/precision/recall/F1/AUC,
что и у baseline. Для сравнения r=8/16/32 используйте **val F1**, сохраняя прочие параметры одинаковыми.
LoRA не обязана улучшить baseline; это проверяется результатами эксперимента.

Без `--quantized` работает обычная LoRA. На CPU это годится для маленькой технической проверки,
а полноценное обучение DeepSeek разумнее выполнять на GPU. 4-битный путь предназначен для CUDA.

Каждый запуск сохраняет:

- `adapter/` — только обученные LoRA-веса, конфигурацию и токенизатор; базовая модель нужна отдельно;
- `checkpoints/` — checkpoint для выбора лучшей эпохи;
- `metrics.json` — метрики, параметры запуска, версии ML-библиотек, историю loss и число усечений;
- `predictions.csv` — pair, истинная label, p_buggy и prediction для анализа ошибок.

Каталог `runs/` исключён из git. Для отчёта вручную перенесите **проверенные настоящие** метрики в
`results/`, отметив split, seed, ревизию весов, r и режим квантования.
Confusion matrix имеет порядок строк/столбцов `[fixed=0, buggy=1]`; порог классификации равен 0.5.

Повторная оценка сохранённого адаптера:

```powershell
python src/llm_baseline.py --quantized --adapter runs/qlora_r16/adapter --output runs/qlora_r16_recheck
```

Используйте те же `--model`, `--revision` и `--max-length`, что при обучении.
Для адаптера обычной LoRA уберите `--quantized`.

## 19. Ошибка No objects to concatenate в 01_data.ipynb

Причиной оказались распакованные файлы `file-0.jsonl` … `file-9.jsonl`: прежний загрузчик
искал только `.jsonl.gz`, получал пустой список и передавал его в `pd.concat`.
Теперь `load_pool` читает оба формата. Если для одного номера есть обе версии, выбирается
сжатая, чтобы не загрузить один shard дважды. Если файлов нет, ошибка показывает полный
путь поиска и ожидаемые имена файлов.

После изменения `src/data_utils.py` перезапустите ядро ноутбука (Restart Kernel), затем
выполните ячейки с начала: уже импортированный модуль автоматически не обновляется.
Если данные лежат в другой папке, укажите её в `RAW_DIR`.
Исправление проверено 12 тестами подготовки данных, включая оба формата, отсутствие
повторной загрузки одного shard и чтение кэша.

## 20. CalledProcessError в 04_deepseek_baseline.ipynb

В проверенном локальном окружении стоит torch 2.15.0+cpu: `torch.version.cuda` равен None,
`torch.cuda.is_available()` — False, bitsandbytes отсутствует. Поэтому запуск с `--quantized`
останавливается до загрузки модели. Наличие NVIDIA-видеокарты само по себе не означает,
что установленный PyTorch умеет использовать CUDA.

Теперь ноутбук показывает сведения об окружении и проверяет CUDA/bitsandbytes заранее.
Вывод дочернего скрипта также передаётся в ячейку, чтобы причина сбоя не скрывалась за
общим CalledProcessError.

Для 4-битного эксперимента используйте GPU runtime Colab с ML-зависимостями. Другой путь —
настроить локальную CUDA-сборку torch и bitsandbytes, затем проверить их совместимость
с видеокартой; в текущем исправлении эти пакеты автоматически не переустанавливались.
Для запуска без сжатия на CPU установите `USE_4BIT=False` в ноутбуке. Такой запуск требует
больше оперативной памяти и занимает больше времени; сначала используйте 8 пар и batch=1.
Это другой режим вычислений: фиксируйте его при сравнении с QLoRA.
