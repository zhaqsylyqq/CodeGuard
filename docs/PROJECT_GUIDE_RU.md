# CodeGuard: руководство по проекту (для команды)

Этот файл объясняет простыми словами, что мы делаем, почему так, что где лежит и как всё запускать.
После него каждый из нас должен уметь объяснить любое решение на защите. Технический первоисточник —
`docs/AGENT_GUIDE.md` (на английском); если что-то расходится, прав он.

Правило, которое действует везде: **число попадает в отчёт, только если его посчитал настоящий запуск,
у которого есть `metrics.json`.** Проверки на крошечных искусственных моделях — это проверки кода, а не результаты.

## 1. О чём проект

**Тема курса:** дообучение (fine-tuning) большой языковой модели для кода методом LoRA / QLoRA на ошибках в Python.

**Основная задача теперь — исправление бага (repair).** На вход модели даём фрагмент кода с одной ошибочной
строкой, на выходе модель должна вернуть **весь исправленный фрагмент**. Правильный ответ известен: это то,
как реальный разработчик исправил код в коммите на GitHub.

**Данные:** CTSSB-1M — около миллиона реальных исправлений «в одну строку» (single statement) из GitHub.
Каждое исправление хранится как *diff* (что убрали, что добавили).

**Модели:** DeepSeek-Coder **instruct** (модель, обученная выполнять инструкции):
1.3B параметров (маленькая, для отладки и локальных прогонов), 6.7B (основная, на сервере),
33B (только как справочная точка без дообучения, по желанию).

**Что осталось от старой задачи:** «по одному фрагменту сказать buggy или fixed» (детекция). Её оставили
как второстепенную часть: честные базовые модели на уровне случайного и одна метрика из модели ремонта
(«fix direction», раздел 9).

## 2. Почему сменили задачу

1. Фрагменты короткие (около 7 строк, медиана 21 токен), а две версии отличаются одной строкой.
   Часто это просто другая строка-литерал (15% пар). Без остального файла по **одному** фрагменту
   невозможно понять, есть ли в нём баг: `x + 1` может быть и ошибкой, и исправлением.
2. Обе обученные модели детекции это подтвердили: TF-IDF — 0,523, BiLSTM — 0,499 accuracy на val
   при 50% у случайного угадывания (раздел 15). Это не ошибка в коде, а свойство постановки.
3. Ремонт на тех же данных поставлен корректно: правильный ответ один и проверяется автоматически.
   К тому же это вторая половина исходной темы — «предложить исправление».

## 3. Исследовательские вопросы (на них отвечает отчёт)

1. Насколько LoRA улучшает ремонт по сравнению с той же моделью без обучения (zero-shot) и с 3 примерами в промпте (3-shot)?
2. Как влияет ранг LoRA (8 / 16 / 32)?
3. Как влияет размер модели (1.3B против 6.7B)?
4. Сколько качества теряет 4-битная квантизация (QLoRA) по сравнению с обычной LoRA?
5. Обгоняет ли маленькая дообученная модель большую необученную (33B zero-shot)? (по желанию)
6. Какие типы багов (`sstub_pattern`) модель исправляет, а какие нет, и почему?
7. Можно ли вообще научиться детекции по одному фрагменту? (базовые модели + один запуск LoRA)

Ответ на каждый вопрос — абзац в отчёте с числом, **включая неудобные результаты**.

| 5 | Делим 80/10/10 **по проектам** | – |
| 6 | Убираем из val/test код, который уже встречался раньше; проверяем утечку | 647 683 |

**Почему по проектам:** код одного проекта похож сам на себя. Если проект попадёт и в train, и в test,
модель может «узнать проект», а не научиться исправлять баги. Проверка утечки (`check_leakage`) показала
0 общих проектов и 0 общих фрагментов между сплитами — и в общем пуле, и в обоих уровнях.

**Почему фильтр по символам и строкам, а не по токенам:** так фильтр не зависит от токенизатора модели,
и одна и та же выборка подходит для любой модели. Длинных выбросов очень мало (112 пар).

### 5.2 Два уровня: small и full

| Уровень | Папка | train / val / test | Для чего |
|---|---|---|---|
| small | `data/processed/small/` | 4000 / 500 / 500 | CPU-модели, отладка, локальная GPU, Colab |
| full | `data/processed/full/` | 50 000 / 2000 / 5000 | сервер, итоговые числа |

`sample_nested` перемешивает каждый сплит **один раз** и берёт начало списка: small — первые 4000,
full — первые 50 000. Поэтому **small целиком входит в full** (это проверено тестом и в ноутбуке).
Результаты на small и full сравнимы: это те же пары, просто их меньше.

У каждой пары есть `pair_id` — её номер в очищенном пуле. По нему соединяются предсказания разных запусков
(нужно для парного сравнения моделей на одних и тех же примерах).

**Колонки:** `pair_id, project, file_path, sstub_pattern` (тип бага), `buggy` (код с багом), `fixed`
(исправленный код), `is_py2`, `buggy_hash, fixed_hash` (отпечатки для поиска дублей), `split`.

### 5.3 Как работает `rebuild_snippets` и почему сохраняются отступы

В diff строка с пробелом в начале есть в обеих версиях, с `-` — только в buggy, с `+` — только в fixed.
Первый символ отбрасываем, строки `@@` и `\ No newline` пропускаем.

`normalize_code` убирает пробелы в конце строк и пустые строки, но **оставляет отступы**: в Python отступ меняет
смысл, и исправление «перенёс строку внутрь цикла» — настоящее исправление. Это закреплено тестом.

## 6. Задача ремонта: промпт и обучение (`src/repair_utils.py`)

### 6.1 Один промпт для всего

Один и тот же текст используется для zero-shot, 3-shot, обучения и демо:

````
Fix the bug in the following Python code. It is a fragment of a larger file and contains exactly one
buggy statement. Return the complete corrected fragment in a single Python code block and nothing else.

```python
{buggy}
```
````

Ответ, которому учим модель: блок ```` ```python ... ``` ```` с исправленным фрагментом.

**Chat template** — формат диалога, на котором обучали конкретную instruct-модель (у DeepSeek это
`### Instruction:` / `### Response:` и специальный токен конца ответа `<|EOT|>`). Мы не пишем формат руками,
а берём его из токенизатора (`apply_chat_template`). Так любая модель получает свой родной формат, и `--model`
можно сменить без правок кода.

### 6.2 Маскирование меток (labels)

При обучении модель предсказывает следующий токен. Мы считаем ошибку (loss) **только по ответу** и по токену
конца ответа: у токенов промпта метка `-100`, PyTorch их пропускает. Иначе модель тратила бы силы на то,
чтобы заучить инструкцию и входной код.

Важная деталь: ответ заканчивается **тем же токеном, на котором генерация останавливается** (у DeepSeek —
`<|EOT|>`, id 32021). Если не научить модель ставить этот токен, она не умеет вовремя замолчать.
Это проверяется тестом на настоящем токенизаторе DeepSeek: декодированная часть меток равна ответу плюс `<|EOT|>`.

**Почему токенизируем текст, а не используем `apply_chat_template(tokenize=True)`:** в установленной
transformers 5.19 этот вызов возвращает не список, а объект `BatchEncoding`. Мы рендерим шаблон в текст и
токенизируем его без добавления лишних спецсимволов (BOS уже есть в тексте шаблона).

### 6.3 Длина: ничего не обрезаем

Обрезать код нельзя: обрезанный пример учит модель неправильному. Поэтому:
- при обучении примеры длиннее 768 токенов (промпт + ответ) **выбрасываются и считаются**
  (на small: 9 из 4000 обучающих пар);
- при оценке не выбрасывается ничего; бюджет новых токенов = `min(512, 1,5 × длина входа + 32)`.

### 6.4 3-shot

Три коротких пары из train с разными типами багов (выбираются один раз с seed) показываются перед заданием
как прошлые реплики диалога. Те же три для каждого примера; их `pair_id` записаны в `metrics.json`.

### 6.5 Генерация

Жадная (greedy — всегда самый вероятный токен, без случайности), пачками (batch), с **левым** дополнением
(left padding: короткие промпты дополняются слева, чтобы у всех промптов в пачке конец был в одном месте и
генерация начиналась сразу после промпта). Тест проверяет, что пачка даёт ровно те же ответы, что поштучная генерация.

**Разбор ответа:** берём содержимое первого блока ```` ``` ````; если блока нет — весь текст.
Убираем ровно один перевод строки в начале и в конце, но **не пробелы первой строки** (отступ важен).
`parse_ok` = был ли закрытый блок кода.

## 7. Метрики (`repair_utils.py`, раздел 6.1 руководства)

`norm` = `normalize_code` (без хвостовых пробелов и пустых строк, отступы сохраняются).

| Метрика | Смысл простыми словами |
|---|---|
| **exact match** (главная) | ответ модели после `norm` **в точности** равен исправлению разработчика |
| **changed** | модель вообще что-то изменила; `1 − changed` = доля случаев «просто скопировала вход» |
| **localized** | модель правила ту же строку, что и разработчик (множества изменённых строк пересекаются) |
| **localized_exact** | модель правила **ровно** те же строки, что и разработчик |
| **BLEU** | похожесть текста ответа на исправление; **всегда рядом с copy baseline** |
| **parse_ok** | доля ответов с правильно оформленным блоком кода |
| **fix direction** | см. раздел 9 |

**Какие строки «изменены»:** сравниваем строки buggy и ответа через `difflib` и берём номера строк buggy,
которые не совпали. Чистая вставка считается правкой строки, перед которой вставили.

**Почему BLEU опасен без copy baseline:** buggy и fixed совпадают почти полностью. Если модель просто
вернёт вход без изменений, BLEU будет очень высоким, хотя баг не исправлен. Поэтому рядом печатаем BLEU
«копии входа» (copy baseline) — честная точка отсчёта. У copy baseline exact match = 0 по построению.

**Почему не CodeBLEU:** ему нужен разбираемый код и граф потоков данных, а наши фрагменты — куски файлов,
которые в большинстве не разбираются (`ast` на них падает).

**Опорные точки, которые печатаются всегда:** copy baseline (exact match 0, его BLEU), случайный уровень
для direction (0,5), случайный уровень для локализации (вероятность, что одна случайная правка строки
попадёт в строку разработчика).

**Замечание для защиты:** `localized` засчитывается, если модель переписала весь фрагмент — тогда она
«задела» и нужную строку. Поэтому смотрим и на `localized_exact`, и на exact match.

**Неопределённость:** `bootstrap_ci` — 2000 раз случайно с повторами перевыбираем пары и смотрим, как
меняется среднее; 95%-интервал — середина 95% этих средних. Для главного сравнения (LoRA против zero-shot и
против 3-shot) считаем **парный** bootstrap разницы на одних и тех же test-парах (по `pair_id`).
Для 5000 пар интервал около ±1,4 п.п. при доле около 50% и уже при 10–20% — это расчёт, а не результат.

## 8. Протокол val / test (раздел 6.5)

Серверное окно одно, и запускать его может преподаватель, поэтому **каждый запуск сразу пишет
предсказания и для val, и для test**. Дисциплина обеспечивается при составлении отчёта:

1. Все сравнения и таблицы абляций (ранг, квантизация, размер модели) — **только на val**.
2. `make_report.py` выбирает финальную конфигурацию по **val exact match**, записывает выбор вместе с
   val-таблицей в `results/selection.json` и **только после этого** читает test. Тест это проверяет:
   выбирается лучшая на val модель, даже если на test лучше другая.
3. В главной таблице test-числа только для zero-shot, 3-shot и выбранной LoRA (+33B, если был запуск).
   Test-числа остальных запусков — в приложении с пометкой «не использовалось для выбора».
4. Во время обучения лучший checkpoint выбирается по `eval_loss` на 500 парах **val**, не test.

## 9. Fix direction: детекция из модели ремонта

Для каждой пары считаем две суммы логарифмов вероятностей (teacher forcing — модели подаём правильный
ответ и смотрим, насколько он ей вероятен):

- `s_fwd = log P(fixed | промпт(buggy))` — насколько модель согласна, что buggy исправляется в fixed;
- `s_bwd = log P(buggy | промпт(fixed))` — то же в обратную сторону.

Пара засчитывается, если `s_fwd > s_bwd`. Случайный уровень — 0,5. Смысл: если показать обе версии, знает
ли модель, в какую сторону идёт исправление? Не нужно отдельного обучения, и метрика сравнима для zero-shot,
3-shot и LoRA.

## 10. LoRA и QLoRA: что обучается и почему такие настройки (раздел 5.3)

**LoRA** (Low-Rank Adaptation): исходные веса модели заморожены, а к линейным слоям добавляются две
маленькие матрицы `B·A` ранга r. Обучаются только они — доли процента всех параметров. Сохраняется
маленький адаптер (папка `adapter/`), а базовая модель нужна отдельно.

**QLoRA:** то же, но базовые веса хранятся в 4 битах (формат NF4), а вычисления идут в bf16. Памяти нужно
примерно в 4 раза меньше, ценой возможной потери качества — это и измеряет запуск R8.

| Настройка | Значение | Почему |
|---|---|---|
| какие слои | все линейные проекции блоков: q/k/v/o внимания и MLP (gate/up/down) | имена берутся из самой модели; адаптация MLP обычно помогает генерации |
| ранг r | 16 основной; 8 и 32 — абляция | вопрос 2 |
| alpha | 2 × r | масштаб обновления; при смене r поведение остаётся сопоставимым |
| dropout | 0,05 | лёгкая регуляризация |
| точность | bf16; QLoRA: 4-bit NF4 + bf16 | bf16 стабильнее fp16 (нет переполнений) |
| оптимизатор | AdamW, lr 2e-4, cosine, 3% warmup, weight decay 0 | стандарт для LoRA |
| эффективный batch | 32 = batch на GPU × накопление градиента | на маленькой GPU: 2 × 16 |
| эпохи | 2, ограничены бюджетом времени | окно на сервере фиксировано |
| max length | 768 токенов | покрывает почти все примеры, длинные выбрасываются |
| группировка по длине | включена | меньше дополнения, быстрее |
| seed | 42 | воспроизводимость |

**bf16 против fp16 (найденный баг):** старый `train_lora.py` включал fp16 при весах в bf16; на нашей GPU
в тесте адаптер после обучения оставался нулевым. Теперь режим берётся из реального типа весов.

**Gradient checkpointing** — не храним все промежуточные значения, а пересчитываем их при обратном проходе:
медленнее, но помещается в память.

## 11. Устойчивость обучения (`train_repair.py`)

- **Бюджет времени** `--time-budget-min N`: через N минут обучение аккуратно останавливается, состояние
  оценивается и сохраняется, адаптер записывается, затем идёт оценка. Окно не должно закончиться «ничем».
- **Идемпотентность:** если `metrics.json` уже есть — скрипт сразу выходит. Если есть checkpoint —
  продолжает с него. Если адаптер уже сохранён — только оценивает. Значит, после сбоя достаточно
  **запустить ту же команду ещё раз**.
- **Одна GPU:** если видно больше одной, скрипт останавливается и просит задать `CUDA_VISIBLE_DEVICES`.
  Иначе `Trainer` сам попытается использовать все карты.
- Все эти свойства проверены тестами на крошечной модели.

**Что пишет каждый запуск** в `runs/<имя>/`: `metrics.json` (все метрики и разбивки по типам багов и
Python 2, все аргументы, модель и ревизия, git-коммит, версии пакетов, GPU, время, скорость, число
обучаемых параметров, выброшенные по длине примеры, история loss), `val_predictions.parquet`,
`test_predictions.parquet`, `adapter/` и `train_info.json` (для LoRA).

## 14. Детекция (старый трек, вопрос 7)

- **TF-IDF + логистическая регрессия** (`02_baseline.ipynb`): код → «мешок токенов» с весами;
  линейный классификатор. Учится только на train.
- **BiLSTM** (`src/bilstm.py`): код → последовательность Python-токенов (с INDENT/DEDENT) → embedding →
  двунаправленная LSTM → вероятность «buggy». Словарь только по train, лучшая эпоха по val loss.
- **LLM zero-shot / LoRA** (`llm_baseline.py`, `train_lora.py`): промпт «buggy или fixed?», модель не
  генерирует текст — сравниваем суммарную вероятность ответов ` buggy` и ` fixed`. Один и тот же промпт
  до и после LoRA, поэтому результаты сравнимы. Это старый промпт; он намеренно не менялся.

## 16. Ограничения (честно)

1. Только баги «в одну строку»; выводы не переносятся на любые баги.
2. Фрагменты без остального файла: часть исправлений без контекста угадать невозможно.
3. Exact match не засчитывает **другие** правильные исправления (например, эквивалентную запись).
4. 4,9% кода — Python 2 (определяется регулярками, это эвристика); результаты разбиты по `is_py2`.
5. Ищутся только **точные** дубли; почти одинаковый код с другим именем переменной не находится.
6. Один seed, если не успеем запуски R12.
7. 33B оценивается в 4 битах, то есть это не совсем та же модель, что в 16 битах.
8. Большинство фрагментов не разбираются парсером Python, поэтому нет CodeBLEU.

## 17. Вопросы, которые нам могут задать на защите

**Почему сменили задачу с детекции на ремонт?**
По одному фрагменту без файла метку часто не восстановить; обе обученные модели детекции — на уровне
случайного (0,523 и 0,499). Ремонт на тех же данных корректен и проверяется по реальному исправлению.

**Почему делили по проектам, а не случайно?**
Иначе код одного проекта попал бы и в train, и в test, и модель запоминала бы проект. Проверка показала
0 общих проектов и фрагментов.

**Зачем два уровня данных и почему small входит в full?**
small — для быстрых локальных прогонов, full — для сервера. Вложенность делает их сравнимыми.

**Что такое LoRA и почему не дообучать всю модель?**
Обучаем маленькие матрицы ранга r поверх замороженных весов: в сотни раз меньше обучаемых параметров,
помещается на одну GPU, адаптер весит мегабайты.

**Чем QLoRA отличается от LoRA?**
Базовые веса хранятся в 4 битах (NF4), вычисления в bf16. Экономия памяти; цену в качестве мы измеряем.

**Почему alpha = 2r?**
Масштаб обновления `alpha / r` остаётся постоянным при смене ранга, поэтому сравнение рангов честнее.

**Зачем маскировать промпт значением −100?**
Чтобы loss считался только по ответу: модель учится исправлять, а не повторять инструкцию и вход.

**Почему важно, чтобы ответ кончался токеном `<|EOT|>`?**
На нём генерация останавливается. Если не учить модель его ставить, она продолжает писать лишнее.

**Почему левое дополнение при генерации?**
Модель продолжает текст с конца. При левом дополнении у всех промптов в пачке конец на одном месте,
и новые токены идут сразу после настоящего промпта.

**Почему exact match главная метрика, а не BLEU?**
Версии почти совпадают, поэтому копия входа уже даёт высокий BLEU. Exact match честно говорит,
исправлен ли баг так же, как у разработчика. BLEU показываем только рядом с copy baseline.

**Не завышен ли exact match / не занижен ли?**
Скорее занижен: другое правильное исправление не засчитывается. Это ограничение мы называем.

**Как вы избегаете подгонки под test?**
Все решения на val; `selection.json` пишется до чтения test; лучший checkpoint — по val loss; тест это проверяет.

**Почему test считается сразу в каждом запуске, разве это не подглядывание?**
Окно одно, второй раз запустить не сможем. Числа test пишутся, но выбор делается только по val,
и это записано в файл до чтения test. Test-числа невыбранных моделей идут в приложение.

**Что такое fix direction и зачем она?**
Сравниваем `log P(fixed | buggy)` и `log P(buggy | fixed)`. Если первое больше — модель «знает»,
куда идёт исправление. Случайный уровень 0,5. Это детекция на уровне пары без отдельного обучения.

**Что такое bootstrap-интервал?**
Много раз перевыбираем пары с повторами и смотрим разброс среднего; 95% интервал показывает,
насколько число может «гулять» из-за выборки. Парный bootstrap — то же для разницы двух моделей на одних парах.

**Почему одна GPU на запуск, если на сервере их шесть?**
Шесть карт — шесть независимых запусков параллельно (разные ранги, QLoRA, 1.3B). Так проще и надёжнее,
чем распределённое обучение, и 6.7B с LoRA помещается на одну карту 24 ГБ.

**Что будет, если запуск упадёт посреди окна?**
Запускаем ту же команду ещё раз: скрипт продолжит с checkpoint или сразу перейдёт к оценке.
Бюджет времени гарантирует, что адаптер сохранится до конца окна.

**Почему instruct-модель, а не base?**
Base-модель не следует инструкциям, и zero-shot был бы нечестно слабым.

**Почему фильтр длины по символам, а не по токенам?**
Чтобы выборка не зависела от токенизатора и была одинаковой для любой модели.

## 18. Частые проблемы

- **`UnicodeEncodeError: 'charmap'`** при печати в консоли Windows: выполните `$env:PYTHONIOENCODING='utf-8'`.
- **`torch.cuda.is_available()` = False при наличии видеокарты:** установлен CPU-torch; поставьте CUDA-сборку (раздел 12.1).
- **Активация venv запрещена:** `Set-ExecutionPolicy -Scope CurrentUser -ExecutionPolicy RemoteSigned`.
- **«N GPUs are visible…»:** задайте одну карту: `$env:CUDA_VISIBLE_DEVICES='0'`.
- **Нехватка памяти GPU:** уменьшите `--batch-size` и увеличьте `--accumulation-steps`, чтобы произведение
  осталось 32; для оценки уменьшите `--batch-size` / `--eval-batch-size`.
- **После правки `src/*.py` ноутбук не видит изменений:** Restart Kernel и выполнить ячейки сначала.
- **Предупреждение про symlinks в кэше Hugging Face на Windows:** безопасно, просто кэш занимает больше места.
- **`No objects to concatenate` в `01_data.ipynb`:** не найдены файлы данных; `load_pool` читает и `.jsonl`,
  и `.jsonl.gz` и показывает полный путь поиска.
